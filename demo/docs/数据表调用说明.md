# 数据表调用说明：哪一页 / 哪个模块调用了哪张表

这份文档回答的问题是："网站每一页展示的内容，到底是从 Supabase 的哪张表查出来的？"
配合这次"产品页没有数据"的排查一起写，方便你以后自己改数据或者加字段时，
知道该改哪张表会影响哪些页面。

## 0. 先说清楚整体架构

所有页面的 JS **都不会直接调用 Supabase**，全部要经过 `js/data-service.js`
这一个文件（`DataService` 对象）。页面脚本只调用 `DataService.getXxx()`
这种"语义化"的函数，比如"给我产品列表"、"给我这个分类的详情"，完全不知道
背后是查了几张表、怎么 JOIN 的。这样设计的好处：以后表结构再变（就像这次
从"两级分类"变成"三级分类"），只要改 `data-service.js` 一个文件，所有页面
一行代码都不用动。

调用链固定是这三层：

```
页面脚本 (xxx-page.js)
   ↓ 调用
DataService.getXxx()          ← 对外暴露的"业务函数"，页面脚本只认这一层
   ↓ 内部调用
fetchRawXxx()                 ← 真正发 Supabase 查询的地方，只有这一层知道表名/列名
   ↓ 查询
Supabase 数据表
```

`fetchRawCategories()` / `fetchRawAttributeDefinitions()` / `fetchRawProducts()`
这三个函数各自带了一层"内存缓存"（`categoriesCache` / `attributeDefsCache` /
`productsCache`），所以**同一次刷新页面里，不管调用几次 `getXxx()`，每张表
最多只会真正查询 Supabase 一次**——比如产品中心页会连续调用
`getCategoryTree()`、`getFilterableAttributeDefs()`、`getProducts()` 三个函数，
但 `categories`/`subcategories` 表只会在第一次调用时真正查一次，后面都是读内存。

## 1. 涉及的 Supabase 表一览

| 表名 | 作用 | 被哪个 `fetchRaw*()` 查询 |
|---|---|---|
| `categories` | 顶级大类（如"管道连接产品"） | `fetchRawCategories()` |
| `subcategories` | 二级子类（如"沟槽式卡箍"），带 `category_id` 指回 `categories` | `fetchRawCategories()`（跟 categories 一起拉，拼成同一棵树） |
| `products` | 产品主表，带 `subcategory_id` 指向 `subcategories` | `fetchRawProducts()` |
| `product_images` | 产品图片（主图/副图） | `fetchRawProducts()`（嵌套查询） |
| `product_attribute_values` | 产品的具体规格取值（如"管径=DN80"） | `fetchRawProducts()`（嵌套查询） |
| `product_variants` | 产品的 SKU/规格型号列表 | `fetchRawProducts()`（嵌套查询） |
| `product_documents` → `documents` | 产品关联的技术资料文件 | `fetchRawProducts()`（嵌套查询，两层关联） |
| `attribute_definitions` | 技术参数模板（字段名/单位/是否可筛选），按子类分组 | `fetchRawAttributeDefinitions()` |
| `inquiries` | 询价/联系表单提交的线索，**只写不读** | `submitInquiry()`（直接 INSERT，不走 fetchRaw 层） |

> `categories`/`subcategories` 这两张表在 `data-service.js` 里会被拼成
> **同一个"分类树"数组**（顶级用 `cat-` 前缀、子类用 `sub-` 前缀区分 id，
> 避免两张表各自从 1 开始自增的 id 撞车）。所以下面的"页面 → 表"对照里，
> 只要写到"读分类树"，实际上都是这两张表一起查。

## 2. 每一页具体调用了什么

### 首页 `index.html` （`js/home-page.js`）
- 头部导航栏的"产品分类"下拉大菜单：`DataService.getCategoryTree()` → **`categories` + `subcategories`**（这段逻辑在 `js/ui-common.js` 的 `renderHeader()` 里，所有页面头部都会跑一次，下面不再重复列）。
- "重点推荐产品"卡片区：`DataService.getFeaturedProducts()` → **`products`**（含嵌套的 `product_images`），并回头查一次 **`categories`/`subcategories`** 给每张卡片补上分类名称。

### 产品中心（列表页）`products.html` （`js/products-page.js`）
- 左侧分类树 + 顶部面包屑：`getCategoryTree()` → **`categories` + `subcategories`**。
- 顶部"产品分类总览"树状图（含每个节点产品数量）：`getCategoryTreeWithCounts()` → 在分类树基础上再查一遍 **`products`**，按 `subcategory_id` 分组计数。
- 选中某个分类后出现的"按技术参数筛选"面板：`getFilterableAttributeDefs()` → **`attribute_definitions`**；面板里枚举类型的可选值（比如"材质"筛选器要显示哪几个选项）：`getAttributeOptions()` → **`attribute_definitions`** + **`products`**（要扫一遍产品实际出现过的取值）。
- 右侧产品卡片网格 + 分页：`getProducts()` → **`categories`/`subcategories`**（按分类筛选用）+ **`attribute_definitions`**（按规格筛选用）+ **`products`**（含 4 张嵌套子表：`product_images`/`product_attribute_values`/`product_variants`/`product_documents→documents`）。

### 分类详情页 `category.html` （`js/category-page.js`）
- 整页内容：`getCategoryBySlug(slug)` → **`categories`/`subcategories`**（分类自身信息 + 面包屑 + 子分类列表）+ **`products`**（统计该分类下产品总数、挑出重点推荐产品）。

### 产品详情页 `product.html` （`js/product-page.js`）
- 主体内容（图片、规格参数表、SKU 规格列表、技术资料下载）：`getProductBySlug(slug)` → **`products`**（含全部 4 张嵌套子表）+ **`categories`/`subcategories`**（面包屑/分类名）+ **`attribute_definitions`**（把 `product_attribute_values` 里冷冰冰的 `attribute_definition_id` 翻译成"适用管径 (mm)"这种人能看懂的名字+单位）。
- 底部"相关产品推荐"：`getRelatedProducts()` → **`products`**（同一个子类下的其它产品）。
- 询价表单提交：`submitInquiry()` → 写入 **`inquiries`**。

### 资料中心 `resources.html` （`js/resources-page.js`）
- 全站技术资料列表：`getAllDocuments()` → **`products`**（含 `product_documents→documents` 嵌套）+ **`categories`/`subcategories`**（给每份资料标注"属于哪个分类"）。

### 询价清单页 `quote-cart.html` （`js/quote-cart-page.js` + `js/quote-cart.js`）
- 提交询价：`submitInquiry()` → 写入 **`inquiries`**。清单本身（已加入哪些产品）存在浏览器 `localStorage` 里，不查数据库。

### 联系我们页 `contact.html` （`js/contact-page.js`）
- 联系表单提交：`submitInquiry()` → 写入 **`inquiries`**。

### 关于我们 / 行业方案 / 服务支持 / 客户案例（`about.html` / `industries.html` / `services.html` / `cases.html`）
- 目前都是纯静态文案，对应的 `about-page.js`/`industries-page.js`/`services-page.js`/`cases-page.js` **不调用 `DataService`**，不查任何表（`schema.sql` 里预留了 `articles`/`article_categories` 表，未来要接"新闻资讯/案例研究"可以从这几页接入，现在还没接）。

## 3. 反过来查："改这张表会影响哪些页面"

- **`categories` / `subcategories`**：几乎每一页都会用到——全站头部导航的分类大菜单、首页产品卡片的分类名、产品中心的左侧树+树状图、分类详情页、产品详情页面包屑、资料中心的分类标注。
- **`products`（含 4 张嵌套子表）**：首页主推产品、产品中心列表与统计、分类详情页、产品详情页、相关产品推荐、资料中心。
- **`attribute_definitions`**：产品中心的技术参数筛选器、产品详情页的规格参数表。
- **`documents`**：产品详情页的资料下载区、资料中心页。
- **`inquiries`**：只在询价清单页和联系我们页被写入，任何页面都不会读它（anon key 按 `policy.sql` 只有 INSERT 权限，没有 SELECT 权限，这是有意设计成"只能提交、不能偷看别人的询价记录"）。

## 4. 这次"产品页没有产品"是怎么回事（顺带记录）

真实生产库的分类结构比仓库里 `schema.sql` 设计的"两级"（`categories` 自己
引用自己）多了一层，变成了"三级"：`categories` → `subcategories` →
`products`（通过 `products.subcategory_id` 挂到 `subcategories`，而不是
`schema.sql` 里设想的 `products.category_id` 直接挂到 `categories`）。

旧版 `data-service.js` 还是按"两级"写的，去查 `products.category_id` 这个
真实表里根本不存在的列，Supabase 直接报错，代码里的 `catch` 又把这个错误
静默吞掉、返回空数组——页面上表现就是"一个产品都没有"，但控制台其实是有
报错的（`[DataService] 读取 products 失败 ...`）。

已经按三级结构重写了 `fetchRawCategories()` / `fetchRawAttributeDefinitions()`
/ `fetchRawProducts()` 这三个函数，把 `categories`→`subcategories` 拼成一棵
统一的树、把 `products.subcategory_id` 换算成跟这棵树对得上的 id，后面所有
"分类树"、"按分类筛选"、"分类页/产品卡片显示分类名"的逻辑完全没改一行代码。

**还需要你确认一件事**：`subcategories` 这张表如果是后来单独建的，很可能
还没有给 `anon` 角色开只读权限（Row Level Security 策略）。已经在
`policy.sql` 里补充了对应的 `public_read_subcategories` 策略 SQL，
去 Supabase 后台的 SQL Editor 里跑一下（具体语句见 `policy.sql` 文件末尾
"2026-08 补充"那一段）。如果这一步漏掉，现象会是：产品能显示出来了，
但每个产品卡片上的"分类名称"会显示为空。

另外 `attribute_definitions.category_id` 这次默认按"挂在子类（subcategory）
这一级"处理——如果你后台实际是把技术参数模板挂在大类（category）上，
告诉我一声，`fetchRawAttributeDefinitions()` 里改一个字符就行（把 `"sub-"`
改成 `"cat-"`）。
